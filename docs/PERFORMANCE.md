# 本机性能与资源记录

2026-11-23，使用真实 Grid Demo 的 Performance 页面完成两轮旧新版交替测量。常速滚动从约 44 FPS 提升到约 60 FPS；十万行高速滚动从约 19 FPS 提升到 44.5–47.7 FPS，高速场景仍未达到显示器的 60 Hz。优化降低了重复测量、输入协调和无障碍发布成本。

## 环境与口径

- Apple M3 Ultra（Mac15,14），512 GiB，macOS 27.2.1（26B131），aarch64。A22 32U13 显示器为 60 Hz，物理 4096×2304、逻辑 2048×1152；仅测本机。
- 编译器固定为 `356a4131c7`，release 并保留调试行表。旧版是 Grid `1492809` 和 Scoop `356a4131c7`；新版使用本次 Grid 改动及上游 [#199](https://github.com/scoop-lang/scoop/pull/199)、[#201](https://github.com/scoop-lang/scoop/pull/201) 的 Surface／UI 改动与重建依赖。
- 两版均使用 1440×920 的 Demo 窗口、21 列、固定行高 38、表格高度 510。基准只增加自动滚动和统计，调用同一个生产 `dataGrid`；没有替代网格实现。
- 五个阶段各运行 8 秒，按“旧、新、旧、新”执行。设置 `SCOOP_SURFACE_FPS=1`、`SCOOP_GC_STATS=1`。测量期间没有并发编译、进程采样或 GUI 自动化。
- FPS 使用 Metal `presentedTime` 正值产生的实际呈现记录；排除每阶段首秒及跨阶段区间，以呈现帧数除以对应时长。表中范围表示两次运行的结果。分配和 GC 使用整个阶段的累计差值。
- 第一项强制连续请求绘制，检查呈现上限。普通静止窗口按需停帧，没有持续 FPS 输出；这不表示卡顿。`FrameSubmission.Accepted` 只表示提交接受，不能作为屏幕呈现计数。

原始日志、自动滚动源码副本、旧新版二进制及采样位于相邻 `scoop-work/grid/perf-20261123/`；最终对照为 `logs/baseline-c-run.*`、`final-a-run.*`、`baseline-d-run.*`、`final-b-run.*`，执行入口为 `run_comparison.py`。本地开发工具链 `scoop-work/grid/toolchain/` 已更新为本轮验证过的编译器和库。

## 实际呈现帧率

| 场景 | 旧版 FPS | 新版 FPS |
| --- | ---: | ---: |
| 固定内容连续请求绘制 | 59.83–59.99 | 59.99 |
| 同批行内 1 pt 往返 | 59.99 | 59.99 |
| 1,000 行，600 pt/s | 44.29–44.49 | 59.99 |
| 100,000 行，600 pt/s | 44.13–44.29 | 59.83 |
| 100,000 行，3,000 pt/s | 18.69–18.90 | 44.46–47.69 |

常速场景在 1,000 行与 100,000 行之间保持接近相同帧率。高速仍有掉帧，不能据此承诺所有交互、显示刷新率或机器都达到 60 FPS。

## 分配与 GC

以下为两次运行的均值。分配量是每秒累计分配的 MiB；GC 暂停占比使用阶段内累计暂停时间除以阶段时长。

| 场景 | 每秒分配量：旧 → 新（MiB/s） | GC 暂停占比：旧 → 新 |
| --- | ---: | ---: |
| 固定内容连续请求绘制 | 207.7 → 211.9 | 1.62% → 1.65% |
| 同批行内 1 pt 往返 | 826.4 → 550.5 | 9.11% → 5.10% |
| 1,000 行，600 pt/s | 1,097.2 → 602.7 | 9.06% → 6.09% |

## 改动与剩余开销

- Grid 的表头、正文和内容测宽后的 A→B→A 恢复共享同一份视口输入；行高发现改变计划时才替换。行裁剪区域在行级计算一次。
- UI 测量结果记录是否实际读取布局输入，并传播子节点及试测的依赖。约束、节点版本和其他布局条件未变时，未依赖该输入的内容复用完整测量结果；裁剪、放置与输入几何仍随滚动更新。
- Surface 在整次 paint 内合并输入归属变化的收尾；UI 复用未变化的语义属性与动作，并将帧内的平台快照和激活点发布合并到帧完成。隐藏窗口的逻辑更新仍立即走正常更新队列，丢弃帧保留有效旧几何并发布逻辑变化。

第一轮改动后，高速为 39.4–40.2 FPS。独立高速采样发现语义发布覆盖约 32.3% 的主线程样本，推动了帧完成时统一发布的第二轮优化。最终独立采样中，该比例降到约 26.6%；布局测量栈约 32.4%，测量收尾约 13.6%。布局／新行挂载和必要的几何／平台语义发布仍有较高成本。

采样按匹配 dSYM 符号化完整应用地址，再沿栈归属统计；比例可包含子调用，不能相加为独立阶段。采样会扰动执行，其 FPS 没有进入上面的对照表，也不将样本比例解释为精确帧耗时。

## 工作量与正确性回归

`performance` Cone 使用 1200×600 窗口、列宽 120、表头高 32、纵向 overscan 56，包裹真实单元格内容统计工厂与 measure。它覆盖 6 次预热、32 次横纵步进和 8 次远处跳转。观察器会改变执行成本，因此用来检查工作量和生命周期；详情见 [performance Cone](../tests-cones/performance/README.md)。

下面四个场景与 2026-11-21 记录具有相同输入和步骤。旧数据可在该日期的 Git 历史中查阅；表内新版来自本轮最终原生回归。

| 场景 | 内容 measure：旧 → 新 | View 工厂 | 挂载峰值 | Row 读取 |
| --- | ---: | ---: | ---: | ---: |
| 十万行 × 300 列，固定行高 | 24,928 → 4,510 | 4,510 | 521 | 339 |
| 十万行 × 300 列，首末列冻结 | 24,840 → 4,446 | 4,446 | 518 | 339 |
| 十万行 × 300 列，两列贡献内容高度 | 24,137 → 5,503 | 4,025 | 476 | 290 |
| 百万行 × 300 列，惰性来源、首末列冻结 | 24,840 → 4,446 | 4,446 | 518 | 339 |

管理表额外加入同一批可见行内 1 逻辑像素往返的断言：布局稳定后，工厂与内容 measure 计数不增加。由于新增了该阶段，其累计工厂数不与旧步骤直接比较。五个场景的静止新增帧均为 0，关闭后观测单元格均为 0；定位、滚动及编辑会话也通过关闭检查。

验证包括 Grid 189 个模型用例；最终 `performance`、`window`、`columns`、`heights` 四组原生回归，覆盖真实键盘／系统拼音、列宽试测与恢复、可变行高、阅读锚点、编辑与原生定位。Surface 的 115 个 Input 用例和 1 个 Host 用例通过；UI 的内容、场景、网格无障碍、文本与布局结果五组共 10 个原生用例通过，包含隐藏更新和强制丢弃帧。

AppKit 原生用例按每个 Application 独立进程、前台启动运行；初次合并多个 Application 到一个进程及后台启动导致的测试启动问题已按此方式闭合。最终 Demo release 构建、打包和签名校验通过，实际窗口检查了十万行切换、滚动、页面切换、远端列导航及编辑器打开／取消。

同一规模 Cone 的 40,000 条完整本地查询单次结果：构造 0.038 ms、排序 19.962 ms、两级分组 15.250 ms、透视 35.992 ms、恢复 0.014 ms。分组后 40,144 行，透视为 11 列、144 行，全过程读取 Row 1,123,426 次；这组查询数据没有统计分布，百万行视口回归也不构成百万行全量查询性能结论。
